# Phase 91.12 — comptes locaux et session candidat

Le Gateway expose `/auth/session`, `/auth/antiforgery`, `/auth/login`, `/auth/register` et `/auth/logout` quand la base Identity est configurée. Les écritures exigent le jeton antiforgery transmis dans `X-CSRF-TOKEN`. Les tentatives de connexion et d’inscription partagent une limite de dix requêtes par minute et par adresse IP distante ; Identity verrouille le compte après cinq échecs pendant quinze minutes. Les nouveaux mots de passe doivent contenir au moins douze caractères et un chiffre. Les réponses de session ne sont pas mises en cache.

L’inscription est activée par défaut en environnement Development et désactivée ailleurs. Une installation peut la régler avec `Identity:AllowRegistration`. Elle crée une session cookie de huit heures, avec option de session persistante côté connexion. L’interface Angular comporte une page de connexion/inscription en fichiers `.ts`, `.html` et `.scss`, un garde de navigation, et un proxy local `/auth` vers le Gateway. Les cookies sont `HttpOnly` et `SameSite=Lax`; ils sont `Secure` dès que la requête utilise HTTPS, et toujours hors de Development. En Development, l’exigence HTTPS d’OpenIddict est désactivée pour le Compose local en HTTP ; elle reste active dans les autres environnements.

Configuration requise : `ConnectionStrings:IdentityDatabase` et `OpenIddict:Issuer`, puis application des migrations Identity décrites dans [phases 91.10](phase-91-10.md) et [91.17](phase-91-17.md). Avant le premier compte, configurer `Identity:InitialOwnerId` avec l’UUID propriétaire convenu avec les services métier. En développement avec Compose, `npm start` relaie `/auth` et `/api` vers le Gateway publié sur `http://127.0.0.1:5000`. En déploiement, le frontend et le Gateway doivent être servis sous la même origine pour que la session cookie protège le parcours BFF.

Vérification : compilation du Gateway réussie sans avertissement ni erreur ; compilation Angular réussie. Angular signale des dépassements du budget SCSS déjà présents dans plusieurs pages existantes. Les tests n’ont pas été exécutés.

À suivre : enregistrer idempotemment les clients OpenIddict à partir de secrets de configuration, brancher le consentement et UserInfo, puis valider les jetons d’accès dans les API et isoler leurs données par propriétaire. Le client BFF sera ajouté quand ses identifiants et son URI de callback auront une configuration dédiée ; aucun secret n’est codé en dur.
