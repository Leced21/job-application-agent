# Guide de sécurité

## Périmètre actuel

La topologie Compose décrite ici est destinée au développement sur un poste local. Les ports publiés par défaut sont liés à `127.0.0.1`; les API ne doivent pas être exposées directement à un réseau non fiable. Le Gateway protège les routes proxifiées par session quand Identity est configuré, applique antiforgery aux mutations `/api`, retire les cookies et Bearer du navigateur et transmet des jetons de service côté serveur. Le cookie est `HttpOnly`, `Secure`, `SameSite=Lax`. Les endpoints de connexion et d'inscription sont limités à dix requêtes par minute par IP, et Identity verrouille après cinq échecs pendant quinze minutes.

Profile, Matching, Documents, Applications, Agents et Collection valident une identité sur leurs routes métier. Le Gateway émet un claim `jobagent_owner_id` lié au compte Identity ; les APIs privées filtrent les données candidat à partir de ce claim validé. Les Bearer statiques de compatibilité Profile, Documents, Applications, Agents et Collection ne sont acceptés qu'en `Development` et `Testing`. Les tests d'intégration couvrent les accès croisés dans Profile, Documents, Applications et Agents ; Matching autorise les résultats au moyen du profil résolu pour le compte courant. Le catalogue Job reste lisible publiquement ; ses mutations exigent la politique `JobAdmin`, qui autorise uniquement un propriétaire figurant dans `Job:Admin:OwnerIds`. En local, configurez la liste avec `APPLICATIONS_OWNER_ID` et utilisez un jeton administrateur distinct. Les lectures Collection exigent une identité ; ses imports, collectes, revues et publications exigent aussi un propriétaire autorisé dans `Collection:Admin:OwnerIds`. Cette politique d'administration de catalogue est volontairement distincte des données personnelles candidat. Le jeton local de développement est associé à `Collection:LocalAuth:OwnerId`. Collection publie vers Job avec un secret de service dédié. Garder ces API sur loopback et ne pas publier le Gateway sur Internet.

OpenIddict utilise des clés éphémères uniquement en `Development`. Hors de cet environnement, le Gateway exige sa base Identity et au moins un certificat PFX RSA distinct par usage : signature avec `DigitalSignature`, chiffrement avec `KeyEncipherment`. Chaque certificat doit contenir une clé privée RSA d'au moins 2 048 bits et être valide à la date de démarrage. La configuration principale utilise `OpenIddict__Certificates__Signing__Path`, `OpenIddict__Certificates__Signing__Password`, `OpenIddict__Certificates__Encryption__Path` et `OpenIddict__Certificates__Encryption__Password`. Les chemins relatifs sont résolus depuis le répertoire de contenu ; préférer les chemins absolus pour les secrets montés dans un conteneur. Les clés privées sont chargées en mémoire avec `EphemeralKeySet` et ne sont pas enregistrées dans le conteneur. Pour chaque certificat, définir soit `Password`, soit `PasswordFile` (`OpenIddict__Certificates__Signing__PasswordFile` et `OpenIddict__Certificates__Encryption__PasswordFile` pour les certificats principaux), jamais les deux. `PasswordFile` permet de lire le secret dans un fichier monté en lecture seule (chemin absolu conseillé pour un secret monté dans le conteneur) ; le Gateway retire les seuls retours à la ligne finaux et préserve les espaces du mot de passe. Pour les certificats précédents, utiliser le même réglage sous l'index concerné. Monter les mots de passe et les PFX en lecture seule depuis le gestionnaire de secrets retenu. OpenIddict recommande deux certificats RSA distincts des certificats HTTPS ([documentation officielle](https://documentation.openiddict.com/configuration/encryption-and-signing-credentials)).

Pour créer une paire de test locale, utiliser [le générateur de la phase 97.25](phase-97-25.md) avec Windows PowerShell 5.1 ou plus récent. Il produit des certificats auto-signés réservés aux essais locaux et au staging ; ne pas les utiliser en production. Le générateur ne conserve pas les mots de passe : saisir ceux-ci au lancement, puis enregistrer chacun dans le gestionnaire de secrets choisi. Le dossier de sortie doit être absolu, privé et hors du dépôt. Aucun gestionnaire de secrets de production n'a encore été choisi ou configuré.

Le jeu de reprise de la [phase 97.26](phase-97-26.md) exclut les secrets et les PFX et n'est pas chiffré. Conserver ceux-ci séparément dans un gestionnaire de secrets protégé et tester leur récupération avec les sauvegardes ; ne pas publier les archives PostgreSQL ou RabbitMQ dans les artefacts CI.

Pour un renouvellement avec chevauchement, conserver le nouveau certificat dans le chemin principal et ajouter temporairement les certificats précédents sous `OpenIddict__Certificates__Signing__Previous__0__Path`, `OpenIddict__Certificates__Signing__Previous__0__Password` ou `OpenIddict__Certificates__Signing__Previous__0__PasswordFile`, ainsi que les paramètres équivalents `Encryption`. Les index commencent à zéro et peuvent être répétés (`1`, `2`, etc.). Le Gateway valide et enregistre tous les certificats simultanément ; le JWKS publie les clés de signature disponibles. OpenIddict choisit la clé active en fonction de sa période de validité et de son expiration. Déployer les anciennes et nouvelles clés ensemble avant de retirer l'ancienne, puis attendre l'expiration ou la révocation de tous les jetons et artefacts protégés avec celle-ci. Le [runbook de la phase 97.25](phase-97-25.md) décrit les contrôles à effectuer pendant le chevauchement. Compose force `ASPNETCORE_ENVIRONMENT=Development` et continue donc à utiliser des clés éphémères. L'issuer, les certificats TLS, les noms d'hôtes et les cookies HTTPS exigent aussi une configuration dédiée avant exposition réseau. Les tests d'accès croisé établissent le cloisonnement applicatif local ; avant un déploiement, il reste à vérifier l'attribution des propriétaires historiques, les migrations et les comptes réels sur une copie contrôlée des données.

## Règles pour l'installation locale

- Copiez `.env.example` vers `.env`, remplacez chaque valeur factice par un secret local distinct et vérifiez que `.env` est ignoré par Git avec `git check-ignore .env`. Ne partagez jamais le contenu du fichier ou les sorties de commandes qui affichent les variables.
- Gardez les URL d'écoute hôte sur `127.0.0.1`. Ne remplacez pas les binds par `0.0.0.0` pour résoudre un problème de connexion.
- Ne réutilisez pas les valeurs de démonstration, jetons locaux ou certificats éphémères dans une installation persistante.
- Ne placez ni CV, ni données personnelles, ni jeton, ni chaîne de connexion dans un ticket, un log partagé ou un dépôt. Avant de transmettre des logs, retirez les en-têtes, identifiants et contenus sensibles.
- Gardez les workers d'événements et le fournisseur Ollama désactivés tant que leur dépendance n'est pas configurée et contrôlée. Les appels à un modèle peuvent contenir les extraits de profil/offre nécessaires à la tâche ; garder Ollama sur `127.0.0.1` et `OLLAMA_NO_CLOUD=1` si le mode local sans cloud est requis.
- Les routes d'inscription ne remplacent pas la vérification de propriétaire. Les tests d'accès croisé des APIs candidat doivent rester dans les suites de régression ; les comptes réels ne peuvent accéder aux données historiques qu'après attribution explicite de leur propriétaire.
- Sauvegardez les volumes avant une migration. `docker compose down -v` supprime les volumes et leurs données ; ne l'utilisez pas comme dépannage générique.

## Contrôles obligatoires avant toute exposition réseau

La liste ci-dessous est un seuil de release, pas une affirmation que ces contrôles sont déjà satisfaits :

1. Provisionner les certificats OpenIddict via le gestionnaire de secrets, puis tester HTTPS de bout en bout, le chevauchement/rotation et la sauvegarde/restauration des clés, les domaines et les cookies adaptés.
2. Retirer les secrets de démonstration et jetons statiques des déploiements ; stocker les secrets dans le gestionnaire de secrets retenu et définir leur rotation.
3. Fermer les ports directs des API, bases et RabbitMQ. N'exposer que le point d'entrée TLS requis et confirmer les règles réseau depuis l'extérieur du poste.
4. Exécuter l'inventaire en lecture seule de la [phase 97.29](phase-97-29.md), examiner les UUID historiques sur une copie anonymisée et répéter localement le scénario multi-compte de la [phase 97.30](phase-97-30.md). La [phase 97.28](phase-97-28.md) réattribue seulement l'unique profil historique sans propriétaire lorsque l'UUID correspond au propriétaire initial Gateway ; elle refuse les cas ambigus. Le test Compose exerce la frontière Profile via deux comptes OIDC ; les autres APIs candidat gardent leurs suites d'accès croisé. Job contrôle ses mutations par `Job:Admin:OwnerIds`, Collection contrôle ses mutations par `Collection:Admin:OwnerIds` et publie vers Job avec un secret distinct.
5. Valider limites de débit, taille et type des fichiers, politiques CORS/CSP, journaux sans données sensibles, sauvegarde/restauration et gestion d'incident.
6. Exécuter une CI complète verte, analyser les avis NuGet/npm et CodeQL, puis faire relire et approuver la configuration de déploiement.

Les protections et leur statut sont détaillés dans les phases [91](phase-91-1.md), [94](phase-94-1.md) et dans le [bilan de préparation V1](v1-readiness.md). Les ports et l'architecture locale sont dans [architecture.md](architecture.md) ; les identifiants d'exemple et la procédure d'installation sont dans [windows-install.md](windows-install.md).

Le Gateway épingle `System.Security.Cryptography.Xml` à la version corrigée 10.0.13 ; cette version entraîne également le correctif de `System.Security.Cryptography.Pkcs`. Ce pin évite que la dépendance transitive DataProtection reste sur 10.0.11. Les avis concernés sont [GHSA-7hqp-7c5m-4vq6](https://github.com/advisories/GHSA-7hqp-7c5m-4vq6) et [GHSA-846f-f764-76mx](https://github.com/advisories/GHSA-846f-f764-76mx). La restauration avec ces vulnérabilités configurées en erreurs confirme que les projets concernés résolvent les versions corrigées.
