# Phase 97.12 — appliquer les migrations Identity locales sans démarrer le Gateway

Le parcours d'inscription navigateur dépend des tables ASP.NET Identity et OpenIddict de la base Gateway. Sans ces migrations, le Gateway pouvait tenter d'enregistrer son client BFF au démarrage puis échouer sur `OpenIddictApplications`, avant qu'une migration manuelle puisse être exécutée par le même hôte.

`GatewayIdentityDbContextFactory` crée maintenant le contexte EF directement à partir de la chaîne `ConnectionStrings__IdentityDatabase` ou des variables `IDENTITY_DB_*`. Les commandes EF n'ont donc plus besoin d'exécuter les initialisations HTTP/OpenIddict du Gateway.

Le script `tools/Update-LocalIdentityDatabase.ps1` récupère les paramètres Identity depuis `docker compose config` sans les afficher, refuse un conteneur `identity-db` appartenant à un autre projet, attend la disponibilité du conteneur attendu et applique les migrations. Il n'efface ni ne recrée le volume. Ce script autonome est compatible avec Windows PowerShell 5.1 ; les autres scripts locaux peuvent toujours exiger PowerShell 7. La [phase 97.23](phase-97-23.md) ajoute le contrôle de compatibilité Windows correspondant dans la CI.

Validation le 19 octobre 2026 : build Release de la solution sans avertissement, découverte EF du contexte via la factory avec des identifiants factices (sans connexion à une base), et test d'intégration `Registration_ShouldCreateFirstAndSubsequentAccountsWithSeparateOwners` réussi sur PostgreSQL Testcontainers avec les migrations réelles. L'analyse syntaxique PowerShell et la configuration Compose Identity passent également. Le scénario Chromium d'inscription n'a pas démarré : Playwright n'a pas obtenu le serveur Angular sur `127.0.0.1:4200` dans cet environnement ; le test a été interrompu avant tout parcours navigateur. L'application de la migration sur Compose et l'inscription manuelle restent à faire depuis le poste local avec `tools/Update-LocalIdentityDatabase.ps1`.
