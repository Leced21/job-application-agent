# Phase 91.18 — jetons OpenIddict entre Gateway et Profile

Le Gateway enregistre idempotemment un client confidentiel `OpenIddict:Bff:ClientId` / `OpenIddict:Bff:ClientSecret` au démarrage. Il demande au point `/connect/token` un jeton `client_credentials` pour le propriétaire lié à la session Identity. Le serveur vérifie que ce propriétaire correspond à un compte actif et mappé, puis émet `sub` et `jobagent_owner_id` pour l’audience `jobagent_api`. Le secret du client reste côté serveur ; aucun Bearer n’est envoyé au navigateur.

Le jeton d’accès dure cinq minutes. YARP retire `Cookie` et `Authorization` entrants, puis injecte le jeton OpenIddict sur la route Profile. L’API Profile valide la signature et l’émetteur via la découverte OIDC, exige l’audience `jobagent_api` et dérive le filtre propriétaire du claim validé. Le mécanisme local statique reste temporairement accepté par l’API pour les appels internes historiques ; le Gateway ne l’utilise plus pour la route Profile.

Configuration requise : appliquer d’abord les migrations Identity 91.10/91.17 et rattacher le compte à `OwnerId`. Configurer le même `OpenIddict:Issuer` dans Gateway et Profile, puis définir `OpenIddict:Bff:ClientId` et un secret `OpenIddict:Bff:ClientSecret` d’au moins 32 caractères dans le Gateway. L’API Profile doit pouvoir joindre la découverte OIDC du Gateway en HTTPS. L’issuer doit publier les clés de signature ; en Development elles sont éphémères et les jetons cessent d’être valides au redémarrage. Hors Development, les clés persistantes restent obligatoires.

Les autres API utilisent encore leurs jetons statiques. La validation OpenIddict et le relais d’identité n’y sont pas activés. Le client BFF est autorisé à demander uniquement `jobagent_api`, mais son secret reste une capacité sensible ; garder le Gateway et toutes les API sur des ports privés/loopback et protéger la configuration.

Vérification : l’API Profile, ses tests d’intégration, le Gateway et ses tests compilent. Les tests ne sont pas exécutés ; aucune migration ni base de données n’est modifiée. La documentation OpenIddict confirme la configuration de validation distante avec issuer discovery et l’intégration ASP.NET Core/System.Net.Http : [validation des API](https://documentation.openiddict.com/guides/getting-started/implementing-token-validation-in-your-apis.html), [ASP.NET Core](https://documentation.openiddict.com/integrations/aspnet-core), [System.Net.Http](https://documentation.openiddict.com/integrations/system-net-http).
